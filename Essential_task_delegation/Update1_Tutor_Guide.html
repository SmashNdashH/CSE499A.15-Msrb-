Basics, in plain English

One analogy for everything: sorting rice for stones. You have a huge tray of rice with a few small stones mixed in. Your job is to mark every grain as "rice" or one of three kinds of "stone". Keep this picture in mind for every term below.

Semantic segmentation

Give every pixel a class label. Here the classes are Background, Intact, Damaged and Destroyed. Rice: you label every single grain.

IoU (Intersection over Union)

For one class: the overlap between what you marked and what is true, divided by everything either of you marked. 1 is perfect, 0 is no overlap. IoU = TP / (TP + FP + FN).

mIoU (mean IoU)

The average IoU over the 4 classes. Background is included, and it scores about 0.93, which lifts the average. A small mIoU change can hide a big Destroyed change.

Precision

Of the pixels you called Destroyed, how many really are. Of the "stones" you picked out, how many are real stones. Low precision = many false alarms.

Recall

Of the truly Destroyed pixels, how many you found. Of all the stones in the tray, how many you caught. Low recall = many misses.

Class imbalance

92.77% of pixels are Background and only 0.33% are Destroyed. A model can look "accurate" by saying Background everywhere. A tray that is 93% rice.

Ablation study

Change one thing, keep everything else the same, and measure the effect. Try better light, then a finer sieve, one at a time, so you know which one helped.

Baseline

The reference model that every experiment is compared with. Here: U-Net + ResNet-34, class-weighted CE + Dice, mIoU 0.4619. Your normal sorting method.

Phase gate

A decision rule agreed in advance: if the model reaches mIoU > 0.52 and Destroyed IoU > 0.30, move on; if not, start Phase 2 (more data). "If you still miss too many stones by Friday, buy a new tool."

A tiny made-up example

There are 100 truly Destroyed pixels. The model marks 150 pixels as Destroyed, and 60 of them are right.

  • TP (true positives) = 60, FP (false alarms) = 150 − 60 = 90, FN (misses) = 100 − 60 = 40.
  • Precision = 60 / 150 = 0.40. Recall = 60 / 100 = 0.60. IoU = 60 / (60 + 90 + 40) = 0.32.

IoU punishes both false alarms and misses. That is why a model with high recall can still have a low IoU.

Track A — Data sampling (Aryan Sami)

Concept: two kinds of imbalance

Pixel level: Destroyed is 0.33% of pixels. Image level: Destroyed appears in 37% of images (2,385 of 6,443). So most batches do contain some Destroyed pixels, just very few of them.

Concept: weighted sampling

Instead of drawing every image equally often, draw images with rare classes more often (with replacement). It changes what the model sees, not how mistakes are scored.

Reasoning

Fix the data before touching the model. If rare buildings are seen more often, every later track benefits. Keep batch size 16 so BatchNorm (layers that normalise using batch statistics) stays stable.

Track B — Architecture (Abrar Mohammed Tanzim Alam)

Concept: encoder and decoder

The encoder (ResNet-34) shrinks the image into rich features. The decoder grows them back to a full-size mask. Skip connections pass fine detail from encoder to decoder.

Concept: what an architecture change can do

A better decoder can keep small details (rubble, roof edges) or add context (what surrounds a building). It cannot fix a loss that rewards the wrong thing.

Reasoning

Hold the loss constant (class-weighted CE + Dice) and swap only the decoder, so any change is due to the architecture. (In practice batch size and learning rate also changed; see the Confound column.)

Track C — Loss function (Abdullah Al Noman)

Concept: the loss decides what "wrong" costs

The loss is the score the model tries to lower during training. If misses and false alarms cost different amounts, the model learns a different balance.

Concept: Tversky index

TI = TP / (TP + α·FP + β·FN). With β > α, a miss costs more than a false alarm. With α = β = 0.5 it is plain Dice. It is computed per class and averaged, so every class counts equally, no matter how few pixels it has.

Concept: Lovász-Softmax

A smooth stand-in for IoU that the model can learn from directly (a "convex surrogate"). It brings the training goal closer to the score we report.

Reasoning

Imbalance is mostly a scoring problem: plain cross-entropy is dominated by the 93% Background. Change only the loss, keep U-Net + ResNet-34, resize 512, batch 16, 40 epochs.

Track D — Resolution and inference (Ridita Afrin Riya)

Concept: detail vs context

Images are 1024×1024. Resizing to 512 keeps only 25% of the pixels, so small rubble blurs. Cropping keeps full detail but shows less of the scene (less context).

Concept: test-time augmentation (TTA)

Predict on flipped and rotated copies of the image, undo each change, and average. Satellite images have no "up", so every view is equally valid. Averaging smooths out one-off mistakes.

Concept: sliding window

A model trained on small crops can still label a big image: slide a window across it, predict each window, and average where windows overlap.

Reasoning

Resolution is cheap to test and needs no new model. TTA and sliding window are "free" gains: no retraining, only extra prediction time.

Your track in depth, and the logic of your sprint

U-Net vs U-Net++

U-Net: one long skip connection per level. Fine detail from the encoder jumps straight to the decoder.

U-Net
 enc1 ─────────────────────────────► dec1 ──► mask
   ↓                                  ↑
 enc2 ───────────────────► dec2 ──────┘
   ↓                        ↑
 enc3 ─────────► dec3 ──────┘
   ↓              ↑
 enc4 ──► bottleneck

U-Net++: the long jumps are replaced by a grid of small decoder nodes. Each node takes all earlier nodes on its row plus an upsampled node from the row below. Encoder features are refined step by step before they meet the decoder, which narrows the "semantic gap" (the difference between raw edges and meaningful features).

U-Net++   (→ = dense skip along the row,  ↗ = upsample from the row below)
 X00 ──► X01 ──► X02 ──► X03 ──► X04 ──► mask
  ↓     ↗       ↗       ↗       ↗
 X10 ──► X11 ──► X12 ──► X13
  ↓     ↗       ↗       ↗
 X20 ──► X21 ──► X22
  ↓     ↗       ↗
 X30 ──► X31
  ↓     ↗
 X40

scSE (concurrent spatial and channel squeeze-and-excitation)

A small attention block that learns how much to trust each channel and each pixel, and scales them up or down. It sits inside each decoder block.

feature map  (C channels × H × W)
   ├─► cSE: average each channel over H×W ─► tiny MLP ─► one weight per channel (0..1)
   │        ─► multiply each channel by its weight         ("which features matter")
   └─► sSE: 1×1 conv over channels ─► one weight per pixel (0..1)
            ─► multiply each pixel by its weight            ("where to look")
 output = cSE result + sSE result     (SMP adds the two)

ASPP (atrous spatial pyramid pooling, used in DeepLabV3+)

Several convolutions look at the same features with different "hole" spacing (dilation), so each branch sees a different context size. Then the branches are joined.

encoder features
   ├─ 1×1 conv                      (very local)
   ├─ 3×3 conv, dilation 12         (medium context)
   ├─ 3×3 conv, dilation 24         (wide context)
   ├─ 3×3 conv, dilation 36         (very wide context)
   └─ global average pool           (whole image)
   ─► concatenate ─► 1×1 conv ─► decoder (+ one low-level skip) ─► mask

Why did U-Net++ lower precision and mIoU?

Correction first: U-Net++ did not raise recall. Mean recall is 0.787 against the baseline's 0.791. Per class, Intact recall went up (0.860 → 0.884), Destroyed stayed about the same (0.661 → 0.668), and Damaged went down (0.710 → 0.677).

What clearly changed is precision. It fell in all three building classes: Intact 0.536 → 0.503, Damaged 0.296 → 0.279, Destroyed 0.181 → 0.140. More false alarms mean a lower IoU, so mIoU dropped (0.4619 → 0.4405).

Likely reasons (hypotheses, not proven):

  1. The loss rewards over-prediction. With Destroyed weighted 283×, any model is pushed to paint rare classes generously. Extra fine-detail paths give it more ways to do that, such as speckles on textured roofs and roads.
  2. Training settings also changed: batch 8 instead of 16 and learning rate 5e-4 instead of 1e-4. Noisier, faster training alone could cost precision. With one run each, we cannot separate these effects.

Why didn't scSE help?

  1. Attention only re-weights features. It cannot change what the loss rewards, and the loss still rewards over-prediction.
  2. The difference from plain U-Net++ (−0.0038) is smaller than run-to-run noise (0.0067), so "no measurable effect" is the honest summary.
  3. It cost a lot: 8.0 h vs 4.8 h of training.

Fair next test: U-Net++ (with and without scSE) using the Focal Tversky / phased loss and the baseline's batch size and learning rate.

The logic of your sprint design

One variable per track

If two things change together, you cannot tell which one caused the result. One change per run lets you attribute the gain. Lesson from Update 1: tracks B and D also changed batch size or learning rate, which weakens their conclusions.

Four tracks in parallel

Kaggle gives about 30 GPU hours per person per week, and a 40-epoch run takes hours. Four people testing four different levers at once covers the space in about two weeks.

Phase gates

The targets (mIoU > 0.52, Destroyed > 0.30) were fixed before seeing results. That stops "moving the goalposts" and makes the decision (Phase 2 or not) objective.

Champion Model

Each track finds its best lever alone. The Champion combines the winners, because the real question is whether the gains add up, cancel out, or clash.

b) How is γ applied in our Focal Tversky code?

The notebooks install segmentation-models-pytorch==0.3.4. In that version, TverskyLoss does this:

# simplified from SMP 0.3.4
TI_c   = TP_c / (TP_c + alpha*FP_c + beta*FN_c)   # per class; alpha → false alarms, beta → misses
loss_c = 1 - TI_c                                 # classes absent from the batch get 0, but still count in the mean
loss   = mean(loss_c over the 4 classes) ** gamma # gamma is applied ONCE, after averaging

NOT THE PAPER The original Focal Tversky paper (Abraham & Khan, 2019) uses Σ_c (1 − TI_c)^(1/γ): per class, with exponent 1/γ. With γ = 4/3 that exponent is 0.75. Ours is neither per class nor 1/γ: it is the class average raised to γ.

What γ = 1.33 actually does here. Raising the loss to a power above 1 scales the gradient by γ · L^(γ−1), which shrinks as the loss gets smaller. Worked example (made-up loss values):

Averaged loss LGradient scale, γ = 2.0Gradient scale, γ = 1.33Paper style, exponent 0.75
0.51.001.060.89
0.20.400.781.12

So in our code γ acts like a learning-rate dimmer that eases off as training improves. It does not give rare classes extra focus, because the averaging happens before γ. The class balance in Track C comes from the per-class averaging and β > α, not from γ. Also, C3 changed α, β and γ together, so γ's own effect is unknown.

c) TTA views

CONFIRMED "Both flips" equals a 180° rotation (checked numerically), so the 180° view is counted twice. Only 7 of the 8 views are distinct.

Missing view: the full set of 8 square symmetries has two diagonal flips. View 8 (90° rotation + horizontal flip) is the anti-diagonal flip. The main-diagonal flip (transpose) is missing, for example x.transpose(2, 3). The inverse mappings in the code are all correct.

d) Why 0.4824 in D3 but 0.4757 in D1c?

MOSTLY YES, BUT NOT ONLY Two random effects are mixed together:

  1. Different trained models. D1c and D3 each train their own 40-epoch model from scratch with identical settings (both training tables show 40 epochs). No seeds are fixed, so the weights differ.
  2. Random validation crops. The validation transform is A.RandomCrop, so every evaluation pass scores different pixels.

We cannot separate the two. The useful takeaway: two identical runs differed by 0.0067 mIoU. Treat smaller differences as noise.

What could go wrong when we combine them

  1. U-Net++ was only tested with the weighted CE + Dice loss. With the Tversky loss, its extra detail might help instead of hurting. Its "loss" may not carry over.
  2. Double correction for imbalance. The sampler shows rare images 10× more often, and Tversky already gives rare classes equal weight. Together they may over-predict again and lose precision.
  3. The loss was tested at 512 resize with batch 16. At 768 crops, batch 8 or smaller, the loss behaves differently: fewer images per batch means noisier per-class terms.
  4. TTA was only measured on weighted-CE models. Its gain on a Tversky model is unknown.
  5. Sliding window should use windows the same size as the training crops (768), not 512.
  6. Memory. U-Net++ with 768 crops and a larger encoder forces an even smaller batch.

Viva prep: 8 likely supervisor questions
1. Why did each track change only one thing?
So we can say which change caused the result. If two things change together, the effect cannot be attributed. Where a run had to change batch size or learning rate too, we state it.
2. Your U-Net++ runs used batch 8 and a higher learning rate. How can you blame the architecture?
We can't fully. The result is confounded. We will re-run U-Net++ with the baseline's batch size and learning rate, and with the new loss, before deciding.
3. Is the phased loss (0.5233) really better than Focal Tversky (0.5203)?
Not proven. Two identical runs in our project differed by 0.0067, which is bigger than this 0.003 gap. We need repeated runs with different seeds.
4. Why did Focal Tversky improve mIoU so much?
Mostly by cutting false alarms. Mean precision rose from 0.501 to 0.602. The baseline's weighted cross-entropy (Destroyed weighted about 283×) made it over-predict rare classes.
5. How do you pick the best epoch? Isn't that tuning on the validation set?
Yes. We keep the epoch with the best validation mIoU and report on the same set, so the numbers are slightly optimistic. Next step: a separate held-out test split.
6. Does mIoU include background? Why does that matter?
Yes. Background IoU is about 0.93 and lifts the average. That is why we also track Destroyed IoU separately, and why it has its own gate (> 0.30).
7. Why did 512 random crops do worse than resizing?
That model over-predicts Destroyed (recall 0.847, precision 0.109). A likely reason is too little context per crop. It was also validated on random crops, so the comparison is not exact. 768 crops did slightly better.
8. Which gate have you passed, and what is your plan for the other?
mIoU > 0.52 is passed (0.5233). Destroyed > 0.30 is not (best 0.273). Next: combine the winners in the Champion Model; if Destroyed is still below 0.30, start Phase 2 with external data.
